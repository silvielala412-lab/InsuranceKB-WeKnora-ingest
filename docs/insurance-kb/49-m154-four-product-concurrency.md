# 49 · Mission 154 四路产品级并发

## 这次解决什么

旧运行器虽然能用四个进程解析不同产品的 PDF，但进入模型抽取后仍是一个产品接
一个产品、一个批次接一个批次地跑。M152 的有效运行窗口记录为约 20.76 分钟，而且
这个时间还没包含前面的 PDF 解析。M154 把模型阶段改成最多四款产品同时跑；同一
款产品内部仍按原批次顺序串行，避免前后批次相互覆盖。

## 当前实现

- `ProductConcurrencyProfile.max_products` 控制产品并发，合法范围 1–4，命令行默认 4。
- 每个产品使用独立 Provider client；不会在线程之间共享 `httpx.Client` 和回执数组。
- Schema、Prompt、候选构建、Evidence 校验和 M153 回归合并逻辑未修改。
- 候选和上下文在 Provider 并发开始前统一构建，工作线程只读冻结结果，避免普通
  字典缓存发生线程竞争或重复扫描。
- 所有产品共享一个原子调用预算。每次实际尝试先取得唯一调用号；失败和 429 也计数。
  重试只有在保留全部未开始首轮调用预算后才允许。
- exact HTTP 429 会把后续 Provider 并发从 4 降到 2，再次发生则降到 1；已完成批次
  不重跑，单批次仍沿用最多两次尝试的既有边界。
- 产品即使乱序完成，最终仍按基线产品顺序写出；产品内按 batch index 合并。
- audit 新增 `performance`，记录材料解析、计划/候选、Provider、合并写盘和总耗时，
  以及每产品耗时、每次调用等待/耗时、峰值并发和 429 降级事件。

## 如何使用

现有 `m152_gapfill` 命令保持不变，新增可选参数：

```text
--max-product-concurrency 4
```

可以显式改成 1、2、3 或 4。这里的数字只表示同一时刻最多处理多少款产品，不限制
产品总数、PDF 数量或 Schema 字段数。

## 本地验证

- 全部 V5 测试：55 项通过。
- M154 定向测试：6 项通过；与 M152/M153 合并运行共 18 项通过。
- Ruff：通过。
- `m154_concurrency.py` strict mypy：通过。
- compileall：通过。
- 8 产品 × 每产品 3 个等延迟批次的本地模拟：串行 1.217 秒，四路 0.307 秒，约
  3.96 倍；这只验证调度开销和并行度，不是百炼真实耗时承诺。

Windows 全仓测试收集仍被项目已有的 Unix `fcntl` 依赖阻断；`m152_gapfill.py` 的
全依赖 strict mypy 仍会报告 `ocr.py` 和 `value_constraints.py` 中 3 个既有类型问题。
这些问题没有由 M154 引入，也没有在本 Mission 中扩大范围修复。
